# AirShop 开发任务清单

基于 README 的功能范围拆解的开发任务,按依赖顺序排列,供闲余时间分步推进。
英文版见 [TASKS.md](TASKS.md),两份内容一一对应。

## 使用说明

- 完成一个任务就把 `[ ]` 改成 `[x]`;顺序可以调整,但注意每个里程碑开头的**前置依赖**。
- 粒度按"一个闲余时间段(约 1–3 小时)完成一个任务"设计;大任务拆成了子任务。
- 每完成一个任务,跑一遍 `go test ./...`,里程碑完成时顺手记一行日期。
- 带 ❓ 的是**待决策项**:实现前先定方案,定了以后把结论写在任务后面,避免反复。

## 工作流速查

```bash
airway generate model post         # 生成模型
airway generate migration create_posts
airway db:migrate                  # 执行迁移
airway generate api admin          # 生成 API 命令空间
just generate                      # 由 .templ 重新生成 *_templ.go
go run .                           # 启动服务
go run . repl                      # 带项目模型的 REPL
```

约定:`app/api/<name>_api/` 放路由+action,`app/views/` 放 templ 视图,`app/models/` 放模型(记得注册进 REPL),`app/services/` 放业务逻辑,`db/migrate/` 放迁移 SQL。

## M0 基础设施

前置依赖:无(当前代码为脚手架基线)。

- [ ] 本地环境跑通:`airway db:create && airway db:migrate && go run .`,确认首页可访问
- [ ] ❓ 定公共字段约定:主键类型、`created_at`/`updated_at`、软删除与否,写成一段说明放进本文档或 CONTRIBUTING
- [ ] 前后台布局分离:`app/views/layouts/` 增加 storefront 与 admin 两套布局(顶栏、导航、页脚骨架)
- [ ] 路由分区:前台路由与 `/admin` 后台路由分组,404/403 兜底页面
- [ ] ❓ 金额与库存的存储口径定版(建议金额用最小货币单位的整数,如"分"),后续所有表统一

## M1 商品目录

前置依赖:M0。

### 数据层

- [ ] 迁移:`categories` 表(名称、slug、父分类、排序、启用)
- [ ] 迁移:`products` 表(名称、slug、描述、价格、库存、状态:上架/下架、主图)
- [ ] ❓ 是否需要 SKU 变体(`product_variants`:规格、独立价格库存)?先定,影响表结构
- [ ] 模型与 REPL 注册:`Category`、`Product`(及变体)

### 后台管理

- [ ] admin 分类管理:列表、新建、编辑、删除
- [ ] admin 商品管理:列表(分页、按名称/状态筛选)、新建、编辑、上下架
- [ ] 商品图片上传(对接已有 storage,支持多图,第一张为主图)

### 前台

- [ ] 首页改造:商品展示区(推荐位或最新商品)
- [ ] 商品列表页:分类筛选、分页
- [ ] 商品详情页:图片、价格、库存、描述、加购按钮(按钮先占位,M4 接通)

## M2 用户与认证(手机号注册登录)

前置依赖:M0。

- [ ] 迁移:`users` 表(手机号唯一、密码哈希、昵称、状态)
- [ ] ❓ 登录方式定版:密码 + 短信验证码,还是仅验证码?本地开发先用假验证码(固定值/日志输出),短信服务商后置
- [ ] 注册页/登录页/登出 action
- [ ] 会话:cookie session 落地,登录态中间件(未登录访问受保护页面跳登录)
- [ ] 表单校验与错误提示(手机号格式、重复注册)
- [ ] 服务层:`AuthService`(注册/登录/登出),action 只做参数绑定

## M3 地址簿

前置依赖:M2(地址挂在用户下)。

- [ ] 迁移:`addresses` 表(用户 ID、收件人、手机号、省/市/区、详细地址、是否默认)
- [ ] 用户中心地址 CRUD:列表、新增、编辑、删除、设默认
- [ ] ❓ 省市区数据来源(内置区划数据集,或先用三个文本输入,后置)

## M4 购物车

前置依赖:M1、M2。

- [ ] ❓ 游客购物车策略:仅登录可用,还是游客也行(session 存、登录后合并)?
- [ ] 迁移:`carts` + `cart_items`(商品/变体、数量、加入时价格快照)
- [ ] 加购/改数量/删除/清空 action 与页面
- [ ] 购物车页:金额小计、库存与下架校验(展示不可购买状态)
- [ ] 服务层:`CartService`(校验、合计计算),供结算复用

## M5 订单与结算

前置依赖:M3、M4。

- [ ] 迁移:`orders`(单号、用户、收货地址快照、金额小计/优惠/运费/实付、状态、支付方式)+ `order_items`(商品快照:名称、图、单价、数量)
- [ ] 结算页:选地址 → 选支付方式 → 提交订单(金额由服务端重算,不信任前端)
- [ ] 订单状态机:`pending → paid → shipped → completed`,及 `cancelled / refunded`;状态流转集中在服务层
- [ ] ❓ 下单扣库存策略(下单预扣 + 取消回补,还是支付后扣),定了写在状态机旁
- [ ] 用户中心:订单列表(按状态筛选)、订单详情
- [ ] 取消订单(仅 pending)、订单超时未支付自动取消(定时任务)

## M6 支付

前置依赖:M5。

- [ ] 支付网关抽象:`PaymentGateway` 接口 + 网关注册表
- [ ] 假支付网关(本地/测试一键标记已支付),保证全流程可测
- [ ] ❓ 真实渠道:支付宝 / 微信支付 / Stripe,按目标市场选型后再拆任务
- [ ] 支付回调:验签、幂等、更新订单状态
- [ ] 支付页/收银台跳转与结果页(成功/失败)

## M7 优惠券

前置依赖:M5(金额计算已集中在服务层)。

- [ ] 迁移:`coupons`(类型:满减/折扣、门槛、面值、有效期、总量)+ `coupon_redemptions`(用户×订单核销记录,防重复用)
- [ ] admin 券管理:创建、列表、停用
- [ ] 结算时选券/输码:金额重算集成进订单服务
- [ ] ❓ 取消/退款时券回退策略
- [ ] (可选)用户领券中心

## M8 物流追踪

前置依赖:M5(发货挂在订单上)。

- [ ] 迁移:`shipments`(订单、承运商、运单号、状态、轨迹 JSON)
- [ ] admin 发货:录入承运商+单号,订单转 `shipped`
- [ ] ❓ 轨迹来源:对接查询服务(快递 100 / AfterShip 等,按可用性选型)或先做手动录入节点;定好后补任务
- [ ] 用户中心:订单物流页(时间线展示轨迹)

## M9 管理后台整合

前置依赖:M1–M8 各自的 admin 页面陆续就位。

- [ ] ❓ 管理员体系:独立 `admin_users` 表,还是 users 加角色字段;后台登录与鉴权中间件
- [ ] 仪表盘:今日/近期订单数、销售额、待处理事项(待发货、待退款)
- [ ] 订单管理:列表(状态筛选、搜索)、详情、发货入口、退款操作
- [ ] 各模块 admin 页面体验统一(分页、筛选、空状态、确认弹窗)
- [ ] ❓ 需要的话加操作审计 `admin_logs`
